# 多模态数据检索平台

面向自动驾驶与智能交通的多模态数据接入、理解与检索平台。系统从火山引擎 TOS 中导入道路场景图片和视频，使用火山方舟完成内容理解与向量化，以本机 MySQL 管理业务元数据、Milvus Standalone 提供向量检索，并通过 Vue 3 Web 界面展示任务进度、检索结果和媒体详情。

> **当前状态（2026-09-17）**：火山引擎架构迁移、本机开源基础设施部署、Milvus Standalone 改造和本机应用启动验证已完成。当前服务已停止，MySQL、Milvus、etcd、MinIO 持久化卷保留。TOS AK/SK、目标 ECS 部署及真实 TOS/方舟端到端链路仍待验收。

## 业务问题与平台能力

| 业务问题 | 平台能力 |
|---|---|
| 文件名难以表达道路场景内容 | 使用自然语言描述场景，按语义检索图片和视频 |
| 找到一张场景图后难以继续扩展 | 上传参考图片，通过视觉相似度检索相关媒体 |
| 手工分类重复且口径不一致 | 方舟生成七类自动驾驶标签，支持人工编辑和 AND/OR 筛选 |
| 媒体接入与处理过程不可见 | 按 TOS 前缀批量导入，展示任务阶段、进度、失败原因、取消和重试状态 |
| 检索结果难以复核和流转 | 提供媒体详情、签名 URL 预览、视频拖动和结果导出 |

AI 标签只作为辅助信息，不替代人工核验；标签生成失败不能按成功处理。向量结果按相似度排序，不保证覆盖所有相关媒体。

## 系统架构

业务媒体与 Milvus 内部对象数据采用独立存储：

- **火山引擎 TOS**：保存业务图片和视频，持久化规范 URI `tos://bucket/key`，通过短期签名 HTTPS URL 提供预览和模型访问。
- **Milvus 内部 MinIO**：只保存 Milvus 的向量数据和索引文件，不替代 TOS，也不向宿主机映射端口。

| 层级 | 组件 | 说明 |
|---|---|---|
| Web 应用 | Vue 3、Vite 7、Node.js 静态服务 | 默认监听 `3000`，通过 `/api/` 访问后端 |
| API 与任务 | Python 3.11、FastAPI | 默认监听 `127.0.0.1:8000`，单 worker 执行后台任务 |
| 业务媒体 | 火山引擎 TOS | 私有桶、限定前缀权限、签名 HTTPS URL |
| 多模态理解 | 火山方舟 `POST /responses` | `doubao-seed-2-1-lite-260915` |
| 跨模态向量 | 火山方舟 `POST /embeddings/multimodal` | `doubao-embedding-vision-251215`，显式请求 1024 维 |
| 元数据 | MySQL `8.4.6` | 用户、媒体、标签、任务和历史记录 |
| 向量检索 | Milvus `2.6.23` Standalone | `COSINE/HNSW`，命令 `milvus run standalone` |
| Milvus 元数据 | etcd `3.5.25` | 仅在 Compose 内部网络使用 |
| Milvus 对象存储 | MinIO（`bitnamilegacy/minio:2025.7.23-debian-12-r5`） | 官方 `minio/minio` 镜像已下架，改用仍可拉取的 Bitnami 冻结镜像；凭证必须为强随机值 |
| Milvus 消息存储 | 内置 Woodpecker | Standalone 模式使用 `MQ_TYPE=woodpecker` |

方舟基础地址固定为 `https://ark.cn-beijing.volces.com/api/v3`。每条媒体独立生成一个 1024 维稠密向量；模型、维度、指令版本和集合身份匹配后才能入库或查询。指定模型不可用时应阻止验收，不自动切换到其他模型。

## 核心流程

1. 用户使用 `tos://bucket/prefix/` 创建导入任务。
2. 后端扫描 TOS 对象并将媒体元数据写入 MySQL。
3. 后端为私有媒体生成方舟可访问的签名 HTTPS URL。
4. 方舟理解模型生成道路场景标签，结果写入 MySQL。
5. 方舟向量模型生成 1024 维向量，结果写入 Milvus。
6. 用户使用文本、参考图片或标签组合进行检索。
7. 后端聚合 Milvus 相似度结果与 MySQL 元数据，并返回可预览的签名 URL。

后台任务由单应用进程执行，MySQL 持久化任务状态。进程重启后遗留的运行中任务会标记为中断失败，通过幂等重试继续；系统不承诺恢复内存中的执行现场。

## 演示流程

1. 准备经授权的独立 TOS 测试前缀和 Milvus 集合，确认 MySQL、Milvus 与 TOS 就绪。
2. 登录系统并配置 TOS 和方舟，分别测试 TOS、理解模型与向量模型；模型测试可能消耗配额。
3. 输入 `tos://bucket/prefix/` 导入图片和视频，查看真实处理进度与失败原因。
4. 输入“雨天路口有行人”进行文本检索，或上传道路图片执行视觉相似检索。
5. 组合标签筛选，检查媒体详情、签名预览、视频拖动与导出字段。
6. 对取消、阶段失败和重启中断任务执行幂等重试，确认人工标签未被覆盖。

方舟访问私有媒体时必须使用其网络可访问的签名 HTTPS URL，不能使用 ECS 私网地址。应用 HTTP 存活不代表 TOS、方舟或完整演示流程已经通过。

## 本机部署

运行前需要 Python 3.11、Node.js 22.12+、Docker Engine、Docker Compose V2、Bash 和 curl。真实配置默认从 `backend/.env` 读取，也可通过绝对路径 `APP_ENV_FILE` 指定；脚本不会 `source` 环境文件。

```bash
# 安装依赖并构建前端
PYTHON_BIN=python3.11 bash deploy/install.sh

# 启动基础设施、后端和前端
APP_ENV_FILE="$(pwd)/backend/.env" bash deploy/start.sh --daemon

# 查看基础设施状态
APP_ENV_FILE="$(pwd)/backend/.env" bash deploy/infra.sh status

# 停止应用，再停止容器；默认保留全部持久化卷
bash deploy/stop.sh
APP_ENV_FILE="$(pwd)/backend/.env" bash deploy/infra.sh down
```

基础设施编排位于 `deploy/docker-compose.infrastructure.yml`。MySQL 只绑定 `127.0.0.1:3306`，Milvus 只绑定 `127.0.0.1:19530/9091`，MinIO 和 etcd 不映射宿主机端口。不要使用 `docker compose down -v` 或手工删除 MinIO/Milvus 数据卷。

完整资源要求、环境变量合同、初始化、迁移和故障处理见 [部署指南](../deploy/DEPLOYMENT.md)。

## 安全与运维约束

- `backend/.env` 权限必须为 `600`，不得提交或放入发布包。
- `INFRA_MYSQL_ROOT_PASSWORD`、`INFRA_MINIO_ROOT_USER`、`INFRA_MINIO_ROOT_PASSWORD`、JWT 密钥及管理员密码必须使用独立强随机值。
- MySQL、Milvus、etcd 和 MinIO 端口不得暴露到公网。
- MinIO 是 Milvus 的必要内部依赖，其数据卷不可单独删除。
- 不得将云凭证写入 `VITE_*`，否则会被编译进公开前端资源。
- 单 ECS 部署不具备集群级高可用；生产使用前必须完成云盘快照、MySQL 备份、向量数据备份和恢复演练。

## 迁移与回退

存量迁移按“对象复制与 URI 映射、元数据 dry-run、写入本机 MySQL、使用方舟重新向量化到 Milvus 新集合、核验、前后端成套切换”执行。迁移保留用户、媒体 ID、人工标签和历史记录；旧向量和旧凭证不复用。

回退时恢复旧应用版本、旧配置和原资源，不删除源库、原桶或旧集合。前后端接口包含成套变更，不支持只升级其中一端。
